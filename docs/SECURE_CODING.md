# 취약점 원인과 개선

실습 대상은 종료하지 않은 격리 레거시 사이트(`127.0.0.1:8000`)입니다. 신규 사이트(`intranet.localhost:8001`)는 별도 Compose 프로젝트, DB, 서명 키, 호스트 한정 쿠키를 사용합니다. 레거시 DB·계정·세션은 신규 사이트에 가져오지 않습니다.

## 신규 사이트에 적용한 패치

- 공개 당직 연락망은 이름·부서·계급/직급·내선만 제공합니다.
- 하드코딩된 설정 조회, 내부 토큰 메타데이터, 기존 실행 API와 에이전트 경로는 등록하지 않습니다. 신규 컨테이너 이미지에는 기존 셸 진단 모듈이나 실습 파일을 포함하지 않습니다.
- 로그인은 원격 주소 기준 60초 구간에 최대 10회로 제한합니다. 초과 요청은 `429`와 `Retry-After`를 반환하며, 임의의 전달 헤더는 제한 키로 신뢰하지 않습니다. 계정 발급·비밀번호 변경 시 최소 14자와 Django 비밀번호 검증 정책을 적용합니다.
- 신규 진단은 세션, `inventory.run_diagnostics` 및 POST의 CSRF 토큰을 요구합니다. DB에 등록된 호스트의 최신 점검 기록만 읽으며 명령 실행·네트워크 조회는 하지 않습니다.
- 두 사이트는 로컬 HTTP 교육 환경입니다. 운영 배포용 TLS, SSO, 감사 시스템은 여기서 제공하지 않습니다.

## 레거시 분석 및 개선안

이하의 원인과 기존 접근 제어는 레거시 기준입니다. 레거시의 로그인, 토큰 노출, 진단 구현은 신규 사이트의 패치 적용 범위에 포함되지 않습니다.

이 문서의 Django 소스 경로는 `app/` 기준입니다.

## 1. 직원 안내에서 콘솔 ID 노출

**원인:** 인증 없는 `/staff/`가 유지보수 로그인 ID를 그대로 렌더링합니다.
`operations/templates/inventory/staff.html`, 시드의 `Employee.login_id`.

**개선:**

- 공개 게시판에는 이름·내선만 두고 로그인 ID는 내부 IAM에만 둡니다.
- 필요하면 인증된 인사 담당자 뷰로 분리합니다.

## 2. 약한 비밀번호와 잠금 없음

**원인:** `AUTH_PASSWORD_VALIDATORS = []`, 시드 비밀번호 `maint123`, 로그인 뷰에 실패 횟수 제한이 없습니다.

**개선:**

- Django 기본 `AUTH_PASSWORD_VALIDATORS`를 켜고 길이·복잡도를 강제합니다.
- `django-axes` 또는 캐시 카운터로 실패 N회 후 잠금·지연을 넣습니다.
- 초기 비밀번호는 일회용으로 발급하고 재설정을 강제합니다.
- 가능하면 SSO/패스키를 사용합니다.

## 3. 정상 상태 응답에 고정 토큰 포함

**원인:** 기존 내부 토큰 화면의 상태 조회가 호출하는 `GET /api/internal/metadata/`가 인증된 사용자에게 `settings.OPSWATCH_INTERNAL_TOKEN`을 JSON에 넣습니다. 화면에는 상태만 표시하지만 네트워크 응답에서 토큰을 읽을 수 있습니다. 만료·회전·사용자 바인딩이 없습니다.

**개선:**

- 토큰은 시크릿 매니저에서 발급하고 짧은 TTL·audience를 넣습니다.
- 사용자·세션에 바인딩하고 재사용을 감사합니다.
- 브라우저에 장기 내부 토큰을 보여 주지 않습니다.
- 진단 API는 서버 세션·권한만으로 인가하는 편이 낫습니다.

## 4. 진단 접근 제어와 남아 있는 CSRF 면제

**현재 적용:** `/api/internal/diagnose/`와 `/api/internal/assistant/`는 로그인 세션(없으면 401), `inventory.run_diagnostics` 권한(없으면 403), 기존 고정 토큰을 순서대로 검사합니다. 토큰만으로 세션 없이 호출하거나 일반 계정이 유출 토큰으로 실행하는 것은 허용하지 않습니다. 두 페이지는 비로그인 시 로그인으로 이동하고 권한 없는 사용자에게 403을 반환하며, 메뉴도 해당 권한이 있어야 표시합니다.

기본 시드에서는 `maint`만 진단 직접 권한을 받으며 다른 시드·이관 계정에는 기본적으로 없습니다. 인트라넷 관리자 역할이나 `is_staff` 여부를 진단 허가로 대신하지 않습니다. `/support/`와 메타데이터 API는 기존 로그인 접근을 유지하므로 진단 권한 없는 사용자도 고정 토큰을 볼 수 있습니다.

**남은 약점:** 두 실행 API의 `csrf_exempt`와 고정 공유 토큰은 유지됩니다. 상황실 에이전트는 별도 명령을 만들지 않고 운영자가 입력한 대상을 `run_ping_diagnosis()`에 그대로 넘기므로, 권한 있는 계정의 명령 삽입도 여전히 가능합니다.

**추가 개선:**

- 현재 세션·진단 권한 검사를 유지하고 CSRF 보호를 복원합니다. 별도 서비스 인증이 필요한 경우에는 mTLS·짧은 TTL 서명 토큰을 설계합니다.
- 고정 공유 시크릿을 제거하고 브라우저에 장기 비밀을 노출하지 않습니다.
- 관리 동작은 감사 로그와 2차 확인.

## 5. 명령 문자열 결합 (Command Injection)

**원인:** `operations/services/diagnostics.py`의 `run_ping_diagnosis()`가 사용자 입력을 셸 명령 문자열과 결합해 실행합니다. 이 경로는 격리 컨테이너에서만 활성화되지만, 격리는 취약점 수정의 대체가 아닙니다.

**개선 (필수):**

1. 셸 실행 경로 자체를 제거합니다. 진단은 ORM 조회나 안전한 라이브러리만 사용합니다.
2. 진단 대상을 허용 목록으로만 받습니다. 예: `Server.hostname` 쿼리 결과와 일치하는 값만.
3. 호스트명 정규식을 통과해도 허용 목록이 없으면 거절합니다.
4. 외부 네트워크 진단이 필요하면 인자 리스트와 `shell=False`만 사용하고, 사용자 입력을 명령 문자열에 넣지 않습니다.
